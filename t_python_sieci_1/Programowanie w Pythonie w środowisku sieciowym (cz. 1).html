▲Gniazda

Gniazda (sockets) oraz interfejs API gniazd służą do wysyłania wiadomości przez sieć. Zapewniają formę komunikacji międzyprocesowej (IPC). Sieć może być logiczną, lokalną siecią dla komputera lub fizycznie połączoną z siecią zewnętrzną, z własnymi połączeniami z innymi sieciami. Oczywistym przykładem jest Internet, z którym łączysz się za pośrednictwem usługodawcy internetowego. Gniazda mają długą historię. Najpopularniejszym rodzajem aplikacji gniazdowych są aplikacje klient-serwer, w których jedna strona działa jak serwer i czeka na połączenia od klientów. Ten rodzaj aplikacji zostanie tutaj omówiony. Mówiąc dokładniej, przyjrzymy się API gniazda dla gniazd internetowych, czasami nazywanych gniazdami Berkeley lub BSD. Istnieją również gniazda domeny Unix, których można używać tylko do komunikacji między procesami na tym samym hoście.

▲Interfejs API gniazd

Podstawowe funkcje i metody API gniazd w tym module to: socket(), bind(), listen(), accept(), connect(), connect_ex(), send(), recv() oraz close(). Python zapewnia wygodny i spójny interfejs API, który odwzorowuje bezpośrednio na te wywołania systemowe, ich odpowiedniki w języku C. W ramach standardowej biblioteki Python posiada również klasy, które ułatwiają korzystanie z tych funkcji gniazd niskiego poziomu. Chociaż nie będzie to tutaj omówione, zobacz moduł socketserver, framework dla serwerów sieciowych. Dostępnych jest również wiele modułów, które implementują protokoły internetowe wyższego poziomu, takie jak HTTP i SMTP. Aby uzyskać przegląd, zobacz Protokoły internetowe i wsparcie.

▲Gniazda TCP

Jak wkrótce zobaczymy, utworzymy obiekt gniazda za pomocą socket.socket() i określmy typ gniazda jako socket.SOCK_STREAM. Domyślnym używanym protokołem jest Protokół kontroli transmisji (TCP).Dlaczego warto korzystać z TCP? Protokół kontroli transmisji (TCP):

  • Jest niezawodny: pakiety utracone w sieci są wykrywane i retransmitowane przez nadawcę
  • Dostarcza dane w kolejności: dane są odczytywane przez aplikację w kolejności, w jakiej zostały zapisane przez nadawcę
W przeciwieństwie do TCP, utworzone gniazda UDP (User Datagram Protocol) przy pomocy socket.SOCK_DGRAM nie są niezawodne, a dane odczytane przez odbiorcę mogą być odczytane w nieprawidłowej kolejności. Dlaczego to jest ważne? Sieci są najlepszym systemem dostarczania. Nie ma gwarancji, że Twoje dane dotrą do miejsca docelowego lub że otrzymasz to, co zostało do Ciebie wysłane. Urządzenia sieciowe (na przykład routery i przełączniki) mają dostępną ograniczoną szerokość pasma i własne ograniczenia systemowe. Mają procesory, pamięć, magistrale i bufory pakietów interfejsów, podobnie jak nasi klienci i serwery. TCP odciąża od konieczności martwienia się o utratę pakietów, dane przychodzące poza kolejnością i wiele innych rzeczy, które niezmiennie zdarzają się, gdy komunikujesz się przez sieć. Na poniższym diagramie spójrzmy na sekwencję wywołań API gniazd i przepływ danych dla TCP.

Rys. 1. Przepływ w gniazdach TCP

Lewa kolumna reprezentuje serwer. Po prawej stronie jest klient. Zaczynając od lewej górnej kolumny, zwróć uwagę na wywołania API, które serwer wykonuje, aby skonfigurować gniazdo "nasłuchujące": socket(), bind(), listen(), accept(). Gniazdo odsłuchowe robi dokładnie to, co dosłownie oznacza: nasłuchuje połączeń od klientów. Gdy klient się łączy, serwer wywołuje accept() do zaakceptowania lub zakończenia połączenia. Klient wywołuje connect() aby ustanowić połączenie z serwerem i zainicjować potrójny "uścisk dłoni" (handshake). Krok uzgadniania jest ważny, ponieważ zapewnia, że każda strona połączenia jest osiągalna w sieci, innymi słowy, że klient może połączyć się z serwerem i odwrotnie. Może się zdarzyć, że tylko jeden host, klient lub serwer może wysłać pakiety danych do drugiego. W środku znajduje się sekcja działająca w obie strony, w której dane są wymieniane między klientem a serwerem za pomocą połączeń z wykorzystaniem send() i recv(). Na dole klient i serwer zamykają gniazda przy użyciu close().

▲Klient i serwer Echo

Po zaprezentowaniu przeglądu interfejsu API gniazda i sposobu komunikacji klienta i serwera, stwórzmy naszego pierwszego klienta i serwer, zaczniemy od prostej implementacji. Serwer po prostu powtórzy to, co otrzyma z powrotem do klienta. Poniżej znajduje się kod dla serwera Echo:

#!/usr/bin/env python3

import socket

HOST = '127.0.0.1'  # Standard loopback interface address (localhost)
PORT = 65432        # Port to listen on (non-privileged ports are > 1023)

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
    s.bind((HOST, PORT))
    s.listen()
    conn, addr = s.accept()
    with conn:
        print('Connected by', addr)
        while True:
            data = conn.recv(1024)
            if not data:
                break
            conn.sendall(data)

Przejrzyjmy każde wywołanie API i zobaczmy, co się dzieje: socket.socket() tworzy obiekt gniazda, który obsługuje typ menedżera kontekstu, dzięki czemu można go użyć w instrukcji with. Nie ma też potrzeby wywoływać s.close():

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
    pass  # Use the socket object without calling s.close().

Argumenty przekazane do socket() określają rodzinę adresów i typ gniazda. AF_INET to rodzina adresów internetowych dla protokołu IPv4, SOCK_STREAM jest typem gniazda TCP, protokołu, który będzie używany do transportu naszych wiadomości w sieci. Metoda bind() służy do powiązania gniazda z określonym interfejsem sieciowym i numerem portu:

Address FamilyProtocolAddress TupleDescription
socket.AF_INETIPv4(host, port)host is a string with a hostname like 'www.example.com' or an IPv4 address like '10.1.2.3', port is an integer.
socket.AF_INET6IPv6(host, port, flowinfo, scopeid)host is a string with a hostname like 'www.example.com' or an IPv6 address like 'fe80::6203:7ab:fe88:9c23', port is an integer. flowinfo and scopeid represent the sin6_flowinfo and sin6_scope_id members in the C struct sockaddr_in6.
HOST = '127.0.0.1'  # Standard loopback interface address (localhost)
PORT = 65432        # Port to listen on (non-privileged ports are > 1023)

# ...

s.bind((HOST, PORT))

Wartości przekazywane do bind() zależą od rodziny adresów gniazda. W tym przykładzie używamy socket.AF_INET (IPv4), dlatego argumentem jest 2-krotka: (host, port), gdzie "host" może być nazwą hosta, adresem IP lub pustym ciągiem. Jeśli używany jest adres IP, "host" powinien być ciągiem adresu w formacie IPv4. Adres IP 127.0.0.1 jest standardowym adresem IPv4 interfejsu pętli zwrotnej (loopback), więc tylko procesy na hoście będą mogły połączyć się z serwerem. Jeśli przekażesz pusty ciąg, serwer zaakceptuje połączenia na wszystkich dostępnych interfejsach IPv4. Parametr "port" powinien być liczbą całkowitą od 1 do 65535(0 jest zarezerwowana). Jest to numer portu TCP do przyjmowania połączeń od klientów. Niektóre systemy mogą wymagać uprawnień administratora, jeśli port jest < 1024. Metoda listen() umożliwia serwerowi zaakceptowanie (metoda accept()) połączenia. Powoduje to, że gniazdo jest "nasłuchujące": 

s.listen()
conn, addr = s.accept()

Metoda listen() ma parametr "backlog". Określa on liczbę nieakceptowanych połączeń, na które zezwoli system przed odrzuceniem nowych połączeń. Począwszy od Pythona 3.5, jest opcjonalny. Jeśli nie zostanie określony, wybierana jest wartość domyślna. Jeśli serwer odbiera wiele żądań połączeń jednocześnie, zwiększenie wartości "backlog" może pomóc, ustawiając maksymalną długość kolejki dla oczekujących połączeń. Maksymalna wartość zależy od systemu.

Metoda accept() blokuje i czeka na połączenie przychodzące. Kiedy klient łączy się, zwraca nowy obiekt gniazda reprezentujący połączenie oraz krotkę z adresem klienta. Krotka będzie zawierać (host, port) dla połączenia IPv4 lub (host, port, flowinfo, scopeid) dla IPv6. Zobacz Rodziny adresów gniazd w sekcji odniesienia, aby uzyskać szczegółowe informacje na temat krotek. Mamy teraz nowy obiekt gniazda zwrócony przez accept(). Jest to ważne, ponieważ jest to gniazdo używane do komunikacji z klientem. Różni się od gniazda nasłuchiwania używanego przez serwer do przyjmowania nowych połączeń:

conn, addr = s.accept()
with conn:
    print('Connected by', addr)
    while True:
        data = conn.recv(1024)
        if not data:
            break
        conn.sendall(data)

Po otrzymaniu obiektu gniazda "conn" z accept(), nieskończona pętla "while" jest używana do wywołań conn.recv() w trybie blocking. Odczytuje wszystkie dane wysyłane przez klienta i powtarza je za pomocą conn.sendall(). Jeśli conn.recv() zwróci pusty objekt typu bytes (b''), wtedy klient zamyka połączenie i pętla jest zakończona. Słowo kluczowe "with" jest używane razem z "conn" do automatycznego zamykania gniazda na końcu bloku.

▲Klient Echo

Kod klienta (echo_client.py) może wyglądać następująco:

#!/usr/bin/env python3

import socket

HOST = '127.0.0.1'  # The server's hostname or IP address
PORT = 65432        # The port used by the server

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
    s.connect((HOST, PORT))
    s.sendall(b'Hello, world')
    data = s.recv(1024)

print('Received', repr(data))

W porównaniu z serwerem klient jest dość prosty. Tworzy obiekt gniazda, łączy się z serwerem i wywołuje s.sendall() aby wysłać swoją wiadomość. Na koniec wywołuje s.recv(), żeby odczytać odpowiedź serwera, a następnie wyświetla ją.

Uruchamianie klienta i serwera Echo

Uruchommy klienta i serwer, aby zobaczyć jak się zachowują i sprawdzić co się dzieje. Należy uruchomić terminal lub wiersz poleceń, przejść do katalogu zawierającego skrypty i uruchomić serwer:

$ ./echo_server.py

Po uruchomieniu terminal będzie wyglądał na zawieszony. Jest tak, ponieważ serwer jest uśpiony w trybie blokownia (blocking mode) dla następującego wywołania:

conn, addr = s.accept()

Serwer czeka na połączenie klienta. Teraz należy otworzyć inne okno terminala lub wiersz polecenia i uruchomić klienta:

$ ./echo-client.py 
Received b'Hello, world'

W oknie serwera powinno pojawić się:

$ ./echo_server.py 
Connected by ('127.0.0.1', 64623)

Na powyższym wyniku serwer wydrukował krotkę "addr" zwróconą przez s.accept(). Jest to adres IP klienta i numer portu TCP. Numer portu 64623 najprawdopodobniej będzie inny po uruchomieniu go na komputerze.

Wyświetlanie stanu gniazda

Aby zobaczyć bieżący stan gniazd na hoście, można użyć polecenia netstat. Jest domyślnie dostępne w systemach macOS, Linux i Windows. Oto przykładowe dane wyjściowe po uruchomieniu serwera:

$ netstat -an
Active Internet connections (including servers)
Proto Recv-Q Send-Q  Local Address          Foreign Address        (state)
tcp4       0      0  127.0.0.1.65432        *.*                    LISTEN

Należy zauważyć, że Local Address to 127.0.0.1.65432. Gdyby echo_server.py używał HOST = '' zamiast HOST = '127.0.0.1', netstat pokazałby:

$ netstat -an
Active Internet connections (including servers)
Proto Recv-Q Send-Q  Local Address          Foreign Address        (state)
tcp4       0      0  *.65432                *.*                    LISTEN

Local Address *.65432 oznacza, że wszystkie dostępne interfejsy hosta obsługujące rodzinę adresów będą używane do akceptowania połączeń przychodzących. W tym przykładzie, w wywołaniu socket() został użyty parametr socket.AF_INET odpowiadający protokołowi IPv4. Można to zobaczyć w kolumnie "Proto": tcp4. W powyższym przykładzie pokazane zostały tylko dane dla serwera echa (pozostałe dane zostały usunięte). Prawdopodobnie polecenie netstat -an pokaże znacznie więcej danych wyjściowych, w zależności od systemu, na którym zostanie uruchomiony, W powyższym przykładzie netstat pokazuje, że serwer echa używa gniazda TCP IPv4 (tcp4), na porcie 65432 we wszystkich interfejsach (*.65432) i jest w stanie nasłuchiwania (LISTEN). Innym sposobem, aby to zobaczyć, wraz z dodatkowymi pomocnymi informacjami, jest polecenie lsof pokazujące listę otwartych plików. Jest ono domyślnie dostępne w systemie macOS i można je zainstalować w systemie Linux za pomocą menedżera pakietów. Przykładowy wynik działania dla procesu serwera echa:

$ lsof -i -n
COMMAND     PID   USER   FD   TYPE   DEVICE SIZE/OFF NODE NAME
Python    67982 nathan    3u  IPv4 0xecf272      0t0  TCP *:65432 (LISTEN)

lsof z opcją -i pokazuje COMMAND, PID (identyfikator procesu) i USER (identyfikator użytkownika) dla otwartych gniazd sieciowych. Polecenia netstat i lsof posiadają wiele opcji, które różnią się w zależności od systemu operacyjnego, na którym są uruchamiane. Więcej informacji na temat ich użycia można znaleźć na stronach z dokumentacją (wersja dla systemu Linux): tutaj oraz tutaj. Rys. 2. Komunikacja klient-serwer poprzez interfejs loopback

Podczas korzystania z interfejsu pętli zwrotnej (adres IPv4 127.0.0.1 lub adres IPv6 ::1), dane nigdy nie opuszczają hosta i nie przechodzą do sieci zewnętrznej. Na powyższym schemacie interfejs loopback jest zawarty w hoście. Reprezentuje to wewnętrzną naturę interfejsu pętli zwrotnej, a połączenia i przesyłane przez niego dane są lokalne dla hosta. Dlatego zarówno interfejs pętli zwrotnej i adres IP 127.0.0.1 lub ::1 określany jest jako "localhost". Aplikacje używają interfejsu pętli zwrotnej do komunikowania się z innymi procesami działającymi na hoście oraz dla bezpieczeństwa i izolacji od sieci zewnętrznej, ponieważ jest on dostępny tylko z poziomu hosta. Można to zobaczyć w działaniu, jeśli np. uruchomiony jest serwer aplikacji, który korzysta z własnej prywatnej bazy danych. Jeśli nie jest to baza danych używana przez inne serwery, prawdopodobnie jest skonfigurowana do nasłuchiwania połączeń tylko na interfejsie pętli zwrotnej. W takim przypadku inne hosty w sieci nie mogą się z nim połączyć.

Gdy używa się adresu IP innego niż 127.0.0.1 lub ::1 w swoich aplikacjach, prawdopodobnie jest on przypisany do interfejsu Ethernet, który z kolei jest podłączony do sieci zewnętrznej. Pełni on rolę "bramy" do innych hostów spoza lokalnego otoczenia:
